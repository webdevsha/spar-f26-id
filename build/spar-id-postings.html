How the flag was computed — and the bug we caught

The first pass used a loose substring match (any "ai", "genai", "otomasi"). It flagged 5 postings as AI-required. Spot-checking them showed most were artefacts:

  • komputer — computer literacy in a Teller BRILink ad, counted as AI.
  • AIA — the insurer's name, matched by the letters "ai".
  • mengenai — the ordinary Indonesian word "regarding"; it contains g-e-n-a-i.

Re-run with word-boundary rules on a fixed term list, the honest count is 1 of 288 — one posting, titled "Finance Automation", which is a genuine but narrow hit (the role automates finance workflows; it does not ask for ML skills). Lesson for Akbar's categorisation plan: keyword flags need word boundaries plus a manual spot-check, and the deferred LLM pass is the right call — a naive keyword count would have overstated AI demand by 5×.

Interpretation: in this sample AI requirements are near-absent from advertised BPO and banking postings. That is a finding about advertised entry-level demand — Indonesian bank/BPO ads for frontline and collections roles rarely list tooling. It does not show that AI skills are not used on the job. Widen the sample before drawing an S5 conclusion.

Was this done ethically?

Marks against the checklist the team agreed: robots/ToS, personal data, access gating, re-publication, and honesty about coverage.

PASSrobots.txt respected
karirhub.kemnaker.go.id/robots.txt is User-agent: * → Allow: / with only admin/dashboard/api/login disallowed. We fetched only public /lowongan-dalam-negeri/lowongan/… pages and never touched the disallowed paths.
PASSNo personal data
No applicant names, CVs, e-mail addresses, phone numbers or recruiter contacts were collected. Rows hold company names only, as published in the public advertisement — consistent with data/PERSONAL-DATA-STOP.md.
PASSIdentified crawler + rate limit
Requests carried User-Agent: SPAR-F26-research/0.1 (academic feasibility test) and slept ~0.35 s between pages (~1.5k pages, single-threaded pool of 4). No parallel hammering, no retries against 4xx.
CAVEATNo anti-bot circumvention
We did not spoof tokens, rotate proxies or solve challenges. Where a platform refused us (Kalibrr KJS API 400/404, BCA candidate API 403, JobStreet/Indeed 403) we recorded the refusal and stopped — that is why those arms are absent, not because the data does not exist.
PASSPublic domain only
Every row is PUBLIC: a government portal page (live arm) or its public Internet Archive capture (archive arm). No logins, no paid feeds, no access requests were used.
CAVEATMinimal re-publication
Ad text is truncated to 240 characters and skills/attributes are kept as short fields, so the repo does not become a wholesale mirror of the platform. Full text stays in local scratch only.
CAVEATCoverage-bias caveat stated
The count of rows here is not the number of vacancies that existed. Live listings only survive while open, so the panel is recency-skewed; archive captures are uneven. Every chart below is labelled as a sample, not a census.
CAVEATAdvertised demand ≠ hires
Postings measure advertised labour demand. They do not establish hiring rates, filled positions or employment — the distinction the team flagged for the IMF-inspired scenario work.
Short answer: yes — this slice is public-domain, robots-permitted, rate-limited, contains no personal data, and did not bypass any access control. The two caveats are deliberate: we truncated ad text rather than mirroring the platform, and we refuse to present the sample size as a vacancy count.

What to refine next (and what would change the answer)

Cheap wins

  • Re-run the live crawl monthly; the same script keeps the panel current and turns the sample into a series.
  • Widen keyword harvesting (teller, collection, underwriting, fintech, paylater) — the current 281 is one keyword sweep, not a full month.
  • Pull the Wayback CDX list for the whole year rather than the sampled snapshots, to fill Oct 2025 – Jul 2026.
  • Store full descriptions locally, classify with an LLM pass, ship only the flags — Akbar's "whichever is more convenient".

What still blocks a real S5 panel

  • No historical depth on the live portal: closed postings disappear, so pre-Aug-2026 is archive-only.
  • Kalibrr / bank portals hold better-structured data but are gated — needs permission, not cleverness.
  • Duplicate detection across employer aliases (PT X vs X) is unsolved; the 32 Kasih Anugrah rows are one employer, many city-level postings.
  • Postings ≠ hires. For a hiring-rate signal we need a second data source (employment statistics, or job-board fill indicators).
